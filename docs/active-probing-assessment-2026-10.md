# 主动探测专项加固评估（2026-10）

> 依据 2026-10-05 晚高峰直连复测中观察到的疑似 GFW 主动探测（`docs/benchmark-2026-09.md` §5.4），评估 Mirage 在被主动探测时还能被区分出来的地方，并给出加固建议。文中服务器与客户端均以代号表示（S1、S2、C2），不含任何真实地址。

> **实施状态 (2026-10-06)**: §4 的 **P1 已实施** —— 预热连接池改为「**延迟预连**」:
> 转发路径在**判定要转发的时刻即时建连**(池龄恒 ≈ 0), 认证前读取从「单一 5s 总截止」改为
> 「**静默间隔语义**」且窗口随客户端 RTT 自适应 (`clamp(2×RTT, 100ms, 500ms)`)。§3 描述的
> 8~14s 关闭时间偏差的根因 (池龄传导给真站 idle-timeout) 随之消除, 预期收敛到「静默窗口
> + 服务器→伪装站 RTT」(亚秒级)。代码: `src/proxy/mirage_server/{camouflage.rs,
camouflage_rtt.rs,handshake.rs::read_client_hello}`。静默窗口**可配** (`tuning.client_hello_quiet`,
> 或环境变量 `MIRAGE_QUIET_MULT` / `MIRAGE_QUIET_MIN_MS` / `MIRAGE_QUIET_MAX_MS`)。
> **端到端关闭时间对齐仍需真机复测** —— 已连同 auth-succ/auth-fail 时延差核对、T_quiet
> 标定等一并列入 [`docs/real-machine-verification.md`](real-machine-verification.md) 的 A1–A3
> (进程内单测已覆盖机制: 按需建连 / 静默语义 / 自适应窗口, 但绝对时序差属部署验证项)。

## 1. 观察到的探测

- **时间**：2026-10-05 21:28–22:10（晚高峰），持续约 40 分钟。
- **来源**：6 个国内运营商 IP，其中一段为 5 个相邻地址，属于同一个探测地址池。
- **目标**：S2 上 14 个测试端口中的 **3 个**（v0.12.1 brutal、v0.14.1 不开 brutal、v0.15.2 不开 brutal），其余 11 个端口一次都没碰；同一时段 S1 没有被探测。
- **时序**：每次探测都在测试客户端访问该端口之后 1–15 分钟到达。
- **内容**：共 50 次连接。49 次发送 TLS ClientHello，服务端判定认证失败、转发给真实伪装站；1 次连上后不发任何数据。
- **后果**：没有发生封锁；S2 在探测之后的成功率反而更高（后 6 轮 99.0%）。

**被选中的原因无法从现有数据判断**：3 个被探测的端口与其他端口的访问次数、成功率、下载表现都没有明显区别。公开研究也提到 GFW 的主动探测带有抽样性质。下面的评估因此聚焦在「探测者连上来之后能不能区分」这一点，这是可以实测和加固的部分。

## 2. 区分度实测（C2 直连，v0.15.2，伪装站 speedtest.net）

| 测试 | 真实伪装站 | S1 | S2 | 结论 |
|---|---|---|---|---|
| T1：发出 ClientHello → 收到首字节，比 TCP RTT 多出的时间 | -31ms（跨境路径抖动） | **+7ms** | **+3ms** | 与服务器到伪装站的 RTT（S1 12ms、S2 3.5ms）一致；在几十毫秒的跨境抖动中难以察觉，**低风险** |
| T2：空连接（连上不发数据）多久被关闭 | 64.0s 后 FIN | **55.9s** 后 FIN | **56.0s** 后 FIN | **提前约 8s，可区分** |
| T3：只发半截 ClientHello，多久被关闭 | 60.3s 后 FIN | **46.6s** 后 FIN | **48.0s** 后 FIN | **提前 12–14s，可区分** |
| 明文 HTTP / 随机字节（§5.3） | 回 14 字节后关闭 | 一致 | 一致 | v0.15 已修复 |

此外，伪装站 speedtest.net 的服务器属于 Fastly CDN，而 VPS 的 IP 并不属于 Fastly。这种「SNI 与 IP 对不上」是已知弱点（此前审计已记录，为了 QoS 有意保留），也是被动识别的可能触发点之一。

## 3. T2 / T3 的根因 (历史 —— 已由「延迟预连」修复, 见文首实施状态)

1. 服务端先最多等 5 秒读取完整的 ClientHello（`src/proxy/mirage_server/handshake.rs` `read_client_hello`）。
2. 读不到完整的 ClientHello 时，判定为异常，调用 `reflect_to_camouflage`，从伪装站连接池（`src/proxy/mirage_server/camouflage_pool.rs`；**已删除，现为 `camouflage_rtt.rs` + 按需即时建连**）**取一条预先建好的连接**，把已收到的字节转发给真站。
3. 池中的连接寿命为 15 秒加最多 12 秒的随机抖动（`STREAM_MIN_AGE_S` / `STREAM_AGE_JITTER_S`）。**真站从自己那一侧连接建立时开始计算空闲超时**，所以这条连接在池里放了多久，探测者看到的关闭时间就提前多久，而且每次提前的量都不固定。
4. 实测相符：真站约 60–64 秒关闭，Mirage 在 46–56 秒关闭，相当于池中连接已存在 9–18 秒。

预热池最初是为了消除认证失败分支上「临时建连多一次 TCP 握手」的时延侧信道（v0.4.5-alpha.7）。它解决了 T1，却引入了 T2 / T3 这个空闲超时的侧信道。认证失败后整段 TLS 会话的空闲超时同样会提前，因为用的也是池里的旧连接。

## 4. 加固建议（按优先级）

### P1：转发路径的空闲超时与真站对齐（修复 T2 / T3）—— ✅ 已实施 (延迟预连, 2026-10-06)

| 方案 | 做法 | 效果 | 代价 |
|---|---|---|---|
| **A. 建连即预连（推荐）** | 每个入站连接在 accept 时，就并行地向伪装站发起一条新连接；认证成功则立即关闭这条连接，认证失败或读取异常则用它转发 | 真站的计时起点与探测者连上的时间只差一个服务器到伪装站的 RTT（3–12ms），空闲超时与真站基本一致；ClientHello 从国内到达至少要一个跨境 RTT（约 150ms），预连早已完成，T1 不受影响 | 每条入站连接（包括合法客户端建隧道）都会多一次到伪装站的 TCP 建连与关闭；这些流量发生在 VPS 与伪装站之间，不经过 GFW。预热池可以取消或只作兜底 |
| B. 异常路径改用新连接 | 只有读取异常（空连接、半截数据）时才临时建新连接，认证失败的完整 ClientHello 仍用池 | T2 / T3 偏差从提前 8–14s 变为延后约 5s（服务端先等的 5 秒），仍可区分但更接近；认证失败后整段会话的空闲超时问题仍在 | 改动最小 |
| C. 缩短池中连接寿命 | 把 15+12 秒降到 1–2 秒 | 偏差缩小到 1–2s，但无法消除 | 到伪装站的建连次数大幅增加 |

建议采用 **A**，并补一个端到端测试：分别对真站和 Mirage 端口发空连接、半截 ClientHello、完整的错误 ClientHello，断言三者的关闭时间与真站相差不超过 1–2 秒。

### P2：验证并缓解「SNI 与 IP 不一致」

`install.sh` 已有「SNI/IP 一致性（可选自动搜索）」：从与服务器同一 ASN / 网段中寻找真实的 TLS 站点作伪装。建议设计一个对照实验：两台条件相同的服务端，一台伪装 speedtest.net，一台用同 ASN 的站点；在若干个晚高峰持续观测被主动探测的次数，验证 SNI 与 IP 一致是否能降低被识别率。若结论成立，再考虑让安装脚本默认启用自动搜索。

### P3：探测可观测性（只记录，不封禁）

- 把「认证失败 / 读取异常」事件记录成结构化日志，包括来源 IP、按 /24 聚合的地址段、收到的字节数、ClientHello 的 SNI 与特征、距本端口上一次合法连接的间隔。
- 在 WebUI 或 API 中提供计数，方便发现被探测的时段和规律。
- **不建议自动封禁探测 IP**：真实网站不会这样做，封禁本身就是一种可被探测到的指纹。

### P4：生产服务器升级

目前两台生产服务器的版本分别为 v0.12.1 和 v0.5.0-alpha.5，仍存在 §5.3 中已被 v0.15 修复的识别面：空连接、明文 HTTP、随机字节探测下的回应与真站不一致，以及 ServerHello key_share 跨连接重复。这次观察到的探测里正好出现了空连接探测。由于 v0.15 是协议断代，升级需要客户端（含 Android App）同步更换。

### P5：伪装站离服务器尽量近（低优先级）

T1 多出的时间约等于服务器到伪装站的 RTT。选择离 VPS 近的伪装站即可保持在几毫秒以内；连接池现有的 RTT 检查（`RTT_MAX_US`）可以保留，并在必要时收紧。

## 5. 不建议的做法

- 根据来源 IP 改变行为（例如识别出探测者后直接断开或封禁）：真实网站不会这样做，反而暴露身份。
- 为了降低探测频率而降低吞吐或改变流量模式，缺乏证据支持，现有数据看不出探测与流量特征之间的关系。
