### A1. T2/T3 关闭时间端到端对齐（真站 vs Mirage）✅ 2026-10-08

- **来源**：`docs/active-probing-assessment-2026-10.md` §3/§4 P1。
- **背景**：旧预热池把"连接已存在时长"传导给真站 idle-timeout，探测者看到的关闭时间比真站提前
  8~14s（实测 46.6~56.0s vs 60.3~64.0s）。现方案（见 `docs/client-hello-timing-design.md`）把
  **对齐**交给“推测性预连”（早）、**容错**交给“判定期限”（宽），**预期**偏差收敛到
  「预连触发延迟 + 服务器→伪装站 RTT」（空连接亚秒级）；半截场景若真站在收到数据时**重置**空闲
  计时，则残余偏差 ≈ 判定期限（默认 1s）—— 这一点必须靠本次实测判定。
- **步骤**：对**真站**端口与 **Mirage 服务端**端口分别发三种探测，测"从连上到收到 FIN"的时间：
  1. 空连接（连上不发数据）；
  2. 半截 ClientHello（发 40 字节就停）；
  3. 完整但认证失败的 ClientHello（token 错误）。
  每个形态各 ≥5 次，记录中位数与离散度。
- **采集工具**（已提供，无需手工掐表）：
  ```bash
  cargo run --release --example probe_close_timing -- \
    -t <真站>:443 -t <Mirage服务端>:443 --count 5 --sni <真站域名>
  ```
  **第 1 个 `-t` 给真站作基线**（工具会对比第 2..n 个与第 1 个的 Δp50）。
  逐条记录 `connect_ms` / `first_byte_after_connect_ms` / `close_ms` 并输出 P50/P95/P99。
  目标机无 Rust 工具链时，可本机 `cargo build --release --example probe_close_timing`
  后把 `target/release/examples/probe_close_timing` 拷过去。
- **判据**：`empty` / `partial` 下 |Mirage 关闭时间 − 真站关闭时间| ≤ 1~2s（看 Δp50）。
  **重点关注"提前"方向** —— Δ 为负（提前）即池龄残留的回归信号。
- **备注**：进程内单测已覆盖机制（按需建连、静默语义、自适应窗口），此步只验绝对时序。

#### A1.0 回环冒烟（机制验证 ✅ 2026-10-06；**不等于真机结果**，真机仍 ⬜）

用真 `mirage server` 二进制 + 受控“假真站”（`IDLE=5s`，可切两种计时语义）在回环上对比，
工具与命令模板即上文那条。结果：

| 假真站语义 | `empty` Δp50 | `partial` Δp50 |
|---|---|---|
| 计时从 accept 起算，数据不重置 | **+101ms** | **+101ms** |
| 收到数据即重置计时 | **+102ms** | **+1005ms** |

- 两种情况都 ≈ ① 预连延迟（回环 RTT ≈ 20µs → 取 100ms 下限）；`[CH-GUARD]` 显示
  `preconnect=1`（预连确实被用上）、`bytes`/`pre_tls` 正确、`authed=-`。
- **量化了本设计的关键取舍**：半截场景的残余偏差 = ①（真站不重置，≈0.1s）或 **②（真站重置，实测 1005ms）**
  —— 这正是真机 A1 必须回答的问题，也是 ② 取值的依据。
- 附带确认：除启动 `prewarm` 的 5 条外，只有“每次预连一条”而无后台持续性连接 →「取消常驻池」成立。
- **局限**：回环不跨审查边界，只能验证机制与时序架构，不能代替真机的绝对值与跨境抖动。
- 坑（做真机时也会遇到）：服务端在 `prewarm` 完成前**不进 accept 循环**——若伪装站被黑洞，探测连接会先在
  backlog 里干等（本次假真站不说 TLS，使 prewarm 耗尽 ~5s 超时，导致首轮测量出现 +4.9s 的假偏差）。
  真机测量前应确认服务端日志已出现 `Mirage Server listening` 并等预热带完。

### A2. auth-succ 与 auth-fail 首字节时延差（T1/T5）✅ 2026-10-09（EWMA 自校准在 S1/S2/S3 三节点正式通过验收，反向不对称免疫）

- **来源**：本次改动把 auth-succ 的时序注入由 `1 × cam_RTT` 翻倍到 `2 × cam_RTT`
  （因 auth-fail 现为即时建连 = 建连 RTT + 转发 RTT）。此为**分析值**，需实测核对。
- **步骤**：
  1. 测 **auth-succ**（合法凭据）从"服务端收完 ClientHello"到"首字节发出"的时延；
  2. 测 **auth-fail**（完整但认证失败的 ClientHello）同口径时延；
  3. 各 ≥20 次，比较两者的中位数与分布（不是单次）。
- **采集工具**（同口径，建议同机、同轮、交错采）：
  - auth-fail 侧：`probe_close_timing -t <Mirage服务端>:443 --modes badauth --count 20`
    看 `first_byte_after_connect_ms`（已减去 TCP 建连段）；
  - auth-succ 侧：`mirage-rs test -c config.json --tag <mirage出站>` 报告的 `handshake_ms`
    （同为"建连后 → 认证确认"）。
- **判据**：两者中位数差落在**跨境抖动噪声范围内**（量级 ≤ 个位数 ms），即探测者无法用首字节
  时延稳定分类。若 auth-succ 明显更快 → 注入量偏小（把 `handshake.rs` 里的 `2 ×` 系数调大）；
  明显更慢 → 偏小调小。
- **备注**：改的是 `handshake.rs` 的 `2 × cam_RTT` 系数，与 `MIRAGE_CH_*`（预连/判定参数）无关。

#### A2.3 结论与处置（2026-10-08）

- **判据修正**：原判据"中位数差 ≤ 个位数 ms"过严 —— A2.1 的测量噪声 σ 就有 12~56ms（A2.2 更大）。
  真正要消除的是**系统性偏移**，故判据改为：**|Δp50| 与 |Δ均值| 均应落在同轮测量噪声内（≲ 1σ），
  且不得重现 ~100ms 量级的单向偏移**。
- **根因已定位**：auth-fail = `2 × cam_RTT + P`，`P` 为伪装站/CDN 对 ClientHello 的固有处理底限
  （~100ms，与 RTT 无关）。旧实现只注入 `2 × cam_RTT`，因此**系统性快 ~120ms**。
- **已处置（代码）**：注入改为 `(auth_succ_mult_x10/10 × cam_RTT + auth_succ_offset_ms) × jitter`，
  并进 `tuning.client_hello_guard`（校验 + env：`MIRAGE_CH_AUTH_MULT_X10` / `MIRAGE_CH_AUTH_OFFSET_MS`）。
  **默认按实测调为 `2.0× + 100ms`**（A2.2 中该档最优）；旧 env 名 `MIRAGE_DELAY_MULT_TENTHS` /
  `MIRAGE_DELAY_OFFSET_MS` 仍兼容。另外修了冷启动：**无 RTT 样本时也注入偏置**（旧实现完全不注入）。
  详见 `docs/client-hello-timing-design.md` §4.5。
- **待复测**：用新默认重跑 A2.1（n ≥ 20，同轮交错）。若 S1 仍残余 ~100ms 单向偏移，把
  `auth_succ_offset_ms` 升到 150~200（S1 数据呈 +100ms 即回收 ~111ms 的线性）；若 S2 出现反方向偏移，
  说明两节点 `P` 不同，应取中间值或考虑 §6.2 的自校准方案（直接测量 auth-fail 耗时）。

#### A2.5 伪装站不可达反向不对称免疫验证（2026-10-09，通过 ✅）

针对“伪装站不可达回落合成模板时，固定 offset=100ms 反向制造合法客户端慢于探测”的隐患进行了实机验证。  
- **防御机制**：`observe_connect_failure()` 在建连失败时归零 `cam_rtt_us` 与 `fail_latency_us`；`injection_base_us` 最高优先级守卫拦截使 `inj_us = 0`。
- **实测（强制伪装站连接拒绝，n = 10 成对交替）**：
  - 服务端日志：`fail_us=0, inj_us=0`，完全不注入任何延迟；
  - 客户端实测：$\Delta mean = \mathbf{+1.7\text{ms}}$，标准差 $\sigma = 48.3\text{ms}$，95% 置信区间为 **`[-28.2ms, +31.6ms]`**。
  - **结论**：反向侧信道被彻底消除。

### A3. 计时参数标定（预连触发 ① / 判定期限 ②）✅ 2026-10-09（① 预连收紧 A/B/C 完成，定档推荐 B 档 1×RTT 50~200ms）

- **来源**：`tuning.client_hello_guard`（默认 `preconnect 2 / 100ms / 500ms`、`judge 1000ms`、
  `hard 5000ms`）。设计见 `docs/client-hello-timing-design.md`。
- **标定目标（两个参数各管一事，分别定）**：
  - **② 判定期限**：必须**大于**真实链路的 TCP 重传间隔（TLP≈2×SRTT / RTO≥200ms，退避可达 800ms+），
    否则丢段的合法客户端会被判成探测。它直接等于半截场景的残余偏差 → 在“容忍重传”与“偏差小”
    之间取最小值。
  - **① 预连触发**：定在“合法 ClientHello 到达时间”的高分位**之下**（快客户端不触发预连），
    同时等于空连接场景的偏差量级。
- **采集（服务端 opt-in 度量）**：服务端设 `MIRAGE_CH_MEASURE=1` 重启，每次判定输出一行
  （**Fallback 样本也记** —— 旧版只记“读完整”，被误杀的合法客户端根本不会出现在数据里）：
  ```text
  [CH-GUARD] outcome=complete|fallback|close ch_read_us=<us> bytes=<n> max_gap_us=<us> pre_tls=<0|1> \
             authed=<1|0|-> judge_us=<us> preconnect=<0|1|2> rtt_us=<us>
  ```
  1. **先查误杀**（应为 0；不为 0 则 ② 偏小）：
     ```bash
     journalctl -u mirage-rs-server --since "1 hour ago" | grep CH-GUARD \
       | awk '/outcome=fallback/ && /pre_tls=1/ {match($0,/max_gap_us=([0-9]+)/,m); if (m[1]>=150000) c++} END{print "疑似丢包误杀:", c+0}'
     ```
  2. **再定 ②**：取“合法客户端（`authed=1`）的 `ch_read_us` 上界 + 重传余量”与“误杀计数为 0”的
     最小满足值。
  3. **定 ①**：合法客户端 `authed=1` 的 `ch_read_us` 分布高分位（如 P99）就是“① 必须小于它”的依据；
     `max_gap_us` 小且 `preconnect=2` 的比例反映有多少合法连接触发了预连（越低越好）。
- **调参（无需改 config、无需重编）**：`MIRAGE_CH_PRECONNECT_MULT` / `_MIN_MS` / `_MAX_MS` /
  `MIRAGE_CH_JUDGE_MS` / `MIRAGE_CH_HARD_MS`。
- **附加验收**：`authed=1` 且 `preconnect=2`（预连了但被关掉）的连接，对伪装站只留下一次
  “accept 后无数据即关”的短连接 —— 顺带看这个量是否与入站连接量级相称。
- **备注**：调参定档后把结论写回 `tuning.client_hello_guard` 的文档注释或此处。

#### A3.3 定档结论（2026-10-08）

1. **② 判定期限保持默认 1000ms**。实测确认 `Δ_partial ≈ ② + cam_RTT`（S1：②=500→+746ms、
   1000→+1191ms、1500→+1554ms），是严格线性关系 —— 于是 ② 的选择变成算术：验收门 |Δ| ≤ 1~2s ⇒
   `② ≤ 1s − cam_RTT`。1000ms 在 S1/S2（cam_RTT≈180ms）下给 ~1.2~1.4s，**过门但已用掉大半预算**。
2. **500ms 档暂不推荐作为生产默认（证据不足）**：那 5/5 是通过在**无丢包**链路上（合法 CH 仅 70µs）拿到的，
   根本没有触及 ② 存在的唯一理由 —— 容忍 TCP 重传（TLP≈2×SRTT / RTO≥200ms，退避可到 800ms+）。
   在真实丢包下 500ms 判定期限**会**误杀丢段的合法客户端（即已修的 P1）。
   → **前置条件**：先用 `tc netem loss`（建议 5% / 20% 两档）复测，确认零误杀，再考虑作为可选强隐蔽档。
3. **① 预连触发可收紧（本次新增结论，待验）**：画像显示合法 CH 在 **23~236µs** 内读完（P50 70µs）——
   ClientHello 与握手 ACK **捎带到达**，服务端 accept 时它已在缓冲。所以 ① 里的 `× RTT` 项对合法客户端
   并非必需，而 `Δ_empty ≈ ① + cam_RTT`（实测 0.63~0.68s）。**建议下一轮 A/B**：
   `preconnect_min_ms` 50~100 与削弱 RTT 项（如 `clamp(RTT, 50, 300)`）对比，预期 empty 偏差 → ~0.25s，
   代价是丢包重传的慢合法连接会多触发一条预连（该连接认证成功即关，成本有界）。

#### A3.4 Phase-3 ① 预连收紧 A/B/C 实测收益与损耗分析（S1 / S2 / S3，2026-10-09，通过 ✅）

详见 [`docs/phase3-real-machine-verification-report.md`](phase3-real-machine-verification-report.md)。对比 A 档（1×RTT, 50~150ms）、B 档（1×RTT, 50~200ms）与 C 档（2×RTT, 50~500ms 基线默认）：

1. **空连接探测残余偏差收益（Δp50 相对 fastly 真站基线）**:
   - **C 档**: S1 −18ms / S2 −50ms / S3 −469ms；
   - **B 档 (推荐生产)**: S1 **+39ms** / S2 **+31ms** / S3 **-246ms** —— S1/S2 达到极其卓越的 +30ms 级贴合，且 S3 近场低 RTT 节点偏差减半；
   - **A 档**: S1 −149ms / S2 −119ms / S3 −352ms。
2. **预连建连损耗评测 (`preconnect=2a` vs `2b`)**:
   - 在分段到达间隔 gap 为 100ms / 200ms / 300ms 下全面扫描，三节点全档位下 `2b` 计数均为 **0**（全量 45/45 样本走 `2a` clean abort）；
   - **确认**：在真实弱网分段下收紧预连**零上游伪装站连接损耗**。

#### A3.5 550ms / 750ms 弱网重传容错验证（2026-10-09，通过 ✅）

针对 TCP 超时重传（TLP 200ms -> RTO 退避 800ms+），验证 `judge_silence = 1000ms` 的抗误杀鲁棒性：
- 在 S1、S2、S3 分别注入 `--gap-ms 550` 与 `750` 分段探测；
- **18/18 样本 100% 成功完成认证握手 (`authed=1`)**，未见任何异常 fallback 或丢弃误杀。

## C. 内核 / eBPF 数据面

### C1. TCP listener 分水岭 —— 真机复核 ✅（netns 三段拓扑，2026-10-06）

- **来源**：`docs/deploy-smoke-test.md` §6。netns 已通过（`examples/verify_tc_divert_tcp.sh`），真机复核。
- **判据**：代理 TCP 时反查目标 == 原始目的；`[TPROXY].*TCP` 出现，且不是被 MASQUERADE 转发。
- **实测**（v0.15.2-4-gcf2bb8d，本机 J4105 / kernel 6.1；netns：LAN 设备 — 网关 (mirage client 透明模式, tc_divert + sk_lookup, 8332 段 direct_cidr) — 出口侧 (mirage server + 目标站)，网关 WAN 口 MASQUERADE）：
  - 裸-IP 走代理（文档地址 `203.0.113.80:8080`）：日志 `[TPROXY] TCP … → 203.0.113.80:8080 → [203.0.113.80:8080]` + `[ROUTE] → [proxy]` + `[TUNNEL] 建立`；目标站看到的对端是服务端本机地址，**不是**网关 WAN 地址 → 未被 MASQUERADE 转发。
  - fake-IP 走代理（LAN 经网关 DNS 解析得 `198.18.0.x`）：`[TPROXY] TCP … → 198.18.0.2:8080 → [域名:8080]`，经隧道到达目标。
  - 对照：geoip cn 内地址走直连快路径，目标看到对端 = 网关 WAN 地址（MASQUERADE），无 `[TPROXY]` 日志，符合预期。
  - 局限：netns 模拟，非实体 LAN 设备 / 实体网卡。

### C2. LPM 是否成为 CPU 热点（决定要不要加 flow cache）✅ 不加（netns，2026-10-06）

- **来源**：`docs/deploy-smoke-test.md` §7。
- **内容**：LAN 设备从国内 CDN 持续高速下载（走 `direct_cidr` 直连路径）压满带宽，采样 tc 软中断里
  LPM 查找占比。
- **判据**：若 LPM 占比 <0.1% 核 → **不加** flow cache（避免无失效缓存的泄漏风险）。
- **实测**（同 C1 拓扑，LAN→geoip cn 目标 iperf3 直连上行，`perf record -a -g` 10s，两轮）：
  | 场景 | 吞吐 | gl0 收包 | `trie_lookup_elem` | `tc_divert` 程序 | 对照：内核 `fib_table_lookup` |
  |---|---|---|---|---|---|
  | veth 默认 TSO（大段） | 5.1 Gbps | 1.2 万 pps | 0.05% | 0.08% | — |
  | 关 TSO/GSO/GRO（MTU 包） | 1.44 Gbps | **12 万 pps**（> 千兆线速 8.1 万） | **0.77%** | 0.42~0.48% | 2.3~2.4% |
  - 百分比为 4 核全部采样的占比，折合约 3% 单核；LPM 查找比每包都要做的内核路由查找还便宜。**结论：不是热点，不加 flow cache。**
  - `%soft` 单核最高 42~64%、全核 21~23%，但该值包含同机 iperf 收发两端与 veth 转发的全部软中断，不能归因到 LPM，不按 §7 的 `%soft` 档判定。

### C3. ICMP 假 IP 反射（第一步）✅（netns，2026-10-06）

- **来源**：`brain/pages/icmp-fakeip-reflect.md`；`brain/roadmap.md`。
- **内容**：`bpf_redirect` 回弹 + tc ingress 语义本地难复现，需真机确认（校验和已复算）。
- **判据**：LAN 设备 ping 被代理域名得到来自 fake-IP 的 ICMP 回显，且不泄漏真实目标。
- **实测**（同 C1 拓扑）：LAN `ping -c3 198.18.0.2` → 3/3 回显，RTT 0.07ms（网关本地反射）；网关 LAN 口抓包见 echo request/reply 成对，**WAN 口同时段 ICMP 抓包为空** → 不泄漏。启动日志 `fake-IP ICMP 反射=198.18.0.0/15`。

### C4. ICMP 真隧道（第二步）⏸️ 暂缓

- **来源**：`brain/pages/icmp-fakeip-reflect.md`。
- **理由**：捕获路径三条（AF_PACKET/TUN/无）均待真机且边际价值低，保留第一步本地反射即可。

## D. 传输 / 性能

### D1. UDP mux 带机量 bench ✅ 突破 pool_size（netns + 实链路，2026-10-06；单级 2000 并发通过，翻转场景受 sid 槽限制）

- **来源**：`brain/pages/udp-capacity-findings.md`。
- **内容**：真机 bench 验证 mux 后并发 UDP 流**突破 `pool_size` 硬伤**（此前真机实测两端
  0.5→0.9 部署并发拐点 20→450）。
- **判据**：mux 开启下并发流上限由 `MAX_FLOWS`（4096）而非 `pool_size` 决定。
- **实测**（`scripts/bench_udp_capacity.py`，网关 `pool_size=4`，每流 10 包/秒、64B，拐点 = flow_ok 跌破 95%）：
  | 环境 | `udp_mux=false` | `udp_mux=true` |
  |---|---|---|
  | netns（网关、服务端、echo、压测全在本机 4 核） | 拐点 < 100 | 800 全过，1000 时 71%（拐点 ≈ 1000）；每流 2 包/秒时拐点 ≈ 2000 |
  | 实链路（本机 netns 网关 → S1，RTT ≈ 175ms，echo 在服务端本机） | 拐点 ≈ 60 | 1000 时 flow_ok 100%（丢包 37%），拐点 ≈ 1400 |
  - **pool_size 墙已破**：mux 关时几十条即崩，mux 开 1000+。
  - **上表的斜坡拐点不是并发上限，而是流翻转累积**（2026-10-06 复查）：压测每级都开新源端口，上一级的流要空闲 60s 才释放 sid；
    mux 共 K=4 条隧道 × 每条 512 sid = 2048 个槽，斜坡 800→1000→1200 累计 3000 条，超出部分的新流被丢弃（服务端只每 1000 次告警一次，日志几乎看不到）。
    每级全新启动、单级加压（无累积）时：**2000 并发 flow_ok 99.5%**；2400 时 85%、3000 时 68%，为平缓下降，此时压测进程自身 CPU 已 90%（同机 4 核），属实验环境上限。
  - **接收缓冲修复**（`transparent_udp.rs` 主 socket `SO_RCVBUFFORCE` 4MB，内核报告 8MB）：A/B 各 3 轮，主 socket 丢包由每轮 1405~1776 降到 **0**；
    单级 2000 并发时数据报丢失 5.6% → 3.1%，2400 时 19.1% → 16.0%；flow_ok 与拐点不变（瓶颈不在这里）。
  - 遗留（未改）：高翻转场景下 sid 槽（K×512，60s 空闲回收）会先于 `MAX_FLOWS` 4096 耗尽；如需提升，可调大 K / 每隧道 sid 上限或缩短空闲回收，需另行评估。

### D2. QUIC 定速在干净链路上不超发 ✅（netns + 实链路，2026-10-06）
