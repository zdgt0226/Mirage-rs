## 2. 443 与非 443 端口对照

同一服务端、同一配置，同时监听 TCP 443 / 18443 与 QUIC（UDP）443 / 18449，交错测试。

### 晚高峰（2026-09-29，S1 + S2，C1 + C2 同时测；S1 丢包 ≈ 20%，S2 丢包 45–65%）

- 连通性：16 组合 × 15 次请求，仅零星失败，无封锁迹象。
- 吞吐：无一致的端口规律（同一组合在两台客户端上快慢相反）。
- 唯一疑点：S2 的 TCP 18443 握手中途失败偏多（C1 7 次 / C2 10 次，TCP 443 为 3 / 1 次），C1 后两轮吞吐跌近 0 —— 但当时 S2 丢包 45–65%，无法区分。

### 白天复测（2026-09-30 08:52–09:20，S1 + S2，C1；丢包 0–10%）

| 组合 | S1 | S2 |
|---|---|---|
| TCP 443（30 次请求） | 30/30，中位 608ms | 30/30，589ms |
| TCP 18443 | 30/30，612ms | 30/30，582ms |
| QUIC 443 | 30/30，378ms | 30/30，376ms |
| QUIC 18449 | 30/30，394ms | 30/30，390ms |

吞吐（Mbps，50MB × 5 轮）：

| 组合 | S1 | S2 |
|---|---|---|
| TCP 443（brutal 100） | 90 / 95 / 96 / 93 / 94 | 96 / 97 / 96 / 95 / 97 |
| TCP 18443（brutal 100） | 96 / 94 / 95 / 92 / 87 | 96 / 96 / 96 / 69 / 95 |
| QUIC 443 | 42 / 62 / 64 / 66 / 68 | 49 / 11 / 34 / 45 / 46 |
| QUIC 18449 | 51 / 70 / 45 / 69 / 63 | 45 / 32 / 43 / 37 / 47 |

所有组合握手失败 0 次。

**结论：在这两条线路上，443 与非 443 端口在连通性、延迟、吞吐上均无可测差异；晚高峰 S2 非 443 的异常来自重丢包，而非针对端口。**（⚠️ 白天复测只用了 C1，其流量经网关代理出境、不直接穿过 GFW，「非针对端口」这一点待 C2 直连复测确认，见 §5。） 默认仍用 443（与真实 HTTPS 流量更一致），被占用时改用其它端口不影响性能。

## 3. 与 sing-box 1.13.14 对比（S1，C1）

对比组：

| 定位 | sing-box | Mirage |
|---|---|---|
| 伪装 TLS（主力） | anytls + REALITY（伪装同一站点） | TCP fake-TLS，不开 brutal |

| QUIC | hysteria2（up/down 100） | QUIC 传输（erasure-aware CC，2MB 窗口） |

Mirage 均为默认 tuning（未开 `tls_padding`）；anytls 自带 padding，对比略偏向 Mirage。

| sing-box ss2022 + brutal 100 | 99 | 23.6–26.2 | 23.2–25.1 |

### 3.2 白天公网（2026-09-30，C1 → S1，丢包 ≈ 5%，50MB × 5）

吞吐被线路限制在 20–78 Mbps、波动大：中位 Mirage 31–36 vs sing-box 26–31（仅"略优"）。服务端 CPU s/GB：Mirage 11–16，anytls 29–32，ss2022 14–21，ss2022 + brutal 26–30。内存 RSS：Mirage 7 → 8MB，sing-box 37 → 44MB。

### 3.3 晚间公网（2026-10-02 22:00–22:20，v0.15.1，C1 → S1，丢包 5% 为主、末段升至 20%，50MB × 5）

| 组合 | 吞吐中位 Mbps（范围） | 服务端 CPU s/GB |
|---|---|---|
| **Mirage TCP** | **107**（83–128） | **11–13** |
| sing-box ss2022 | 106（100–119） | 10–12 |
| sing-box anytls + REALITY | 97（68–129） | 16–23 |
| **Mirage TCP + brutal 100** | **92**（83–93） | **10–15** |
| sing-box ss2022 + brutal 100 | 89（84–90） | 31–33 |
| sing-box hysteria2（100） | **81**（61–90） | 66–77 |
| Mirage QUIC | 51（50–54） | 60–69 |

内存 RSS：Mirage 空闲 13MB → 峰值 23MB（含 QUIC 入站）；sing-box 37MB → 68MB。

QUIC 落后原因定位（同时段对照，各 3 轮）：

| 调整 | Mirage QUIC | 同期 hysteria2 |
|---|---|---|
| 流控窗口 2MB → 8MB | 31–46（反降） | 83–88 |

→ 瓶颈不在窗口，而在**拥塞控制策略**：hysteria2 按设定带宽定速发送、遇丢包不退让（与 brutal 同思路）；Mirage QUIC 的 erasure CC 仍随链路自适应降速（比默认 BBR 快约 6 倍，但不及定速）。

### 3.4 QUIC 定速模式实测（2026-10-03 22:50–23:45，C1 → S1，丢包 5–35% 波动）

新增 QUIC 定速模式（复用 `brutal_rate_mbps`，见 `docs/quic-transport-design.md` §5.8）后同时段交错对比（Mbps）：

| 组合 | 结果 |
|---|---|
| sing-box hysteria2（100） | 77–90，中位 ≈ 87 |
| **Mirage QUIC 定速 100（最终版，窗口 rate × RTT / ack_rate²）** | **58–76**（13 轮中 1 轮塌陷到 2.3） |
| Mirage QUIC 定速 100（只补偿一次 / ack_rate） | 63–70 |
| Mirage QUIC erasure CC（改动前默认） | 31–63 |
| Mirage TCP + brutal 100 | 4–32 |

调参对照：固定增益 1.5 → 71–81（但干净链路会超发 1.5 倍，弃用）；流控窗口 4MB → 49–71、8MB → 25–80（无稳定提升）。
服务端 CPU：定速 49–76 s/GB，hysteria2 62–74 s/GB，相当。

结论：定速比 erasure 提升约 30–50%，与 hysteria2 的差距由 37% 缩到约 20–25%；剩余差距不在流控窗口。重丢包（15% 以上）下 QUIC 远胜 TCP。

### 3.5 QUIC 根因定位与补丁验证（2026-10-04，本机 netns + netem）

为摆脱公网波动，在本机用两个网络命名空间 + netem 模拟：单向延迟 90ms（RTT 180ms）、带宽 100 Mbps、队列 1000 包、丢包可调；服务端命名空间跑 Mirage 服务端、sing-box hysteria2 与本机下载源，客户端命名空间跑两边客户端与 curl。50MB × 3 交错（Mbps）：

| 条件 | hysteria2 | 定速 + 2MB 窗口（补丁前） | erasure + 2MB | 定速 + 8MB（补丁前） | **定速 + 8MB（MAX_CHUNKS 8192）** | erasure + 8MB（补丁后） |
|---|---|---|---|---|---|---|
| 下行丢包 10% / 上行 5% | 63–73 | 27–31 | 27–31 | ≈3（断连） | **66–71** | 47–66 |
| 下行丢包 20% / 上行 10% | 50–60 | 20–23 | — | — | **49–61** | 45–51 |
| 无丢包 | 91 | 75 | 64 | 86 | 89 | 90 |
| 无丢包，定速 50 | — | — | — | — | 43–44（不超发） | — |

根因：2MB 流控窗口在丢包时被队头阻塞卡住（≈ 窗口 / 3 RTT），而窗口一放大，quinn 的乱序段上限 `MAX_CHUNKS = 1024` 就会被突破并断连。补丁与取舍见 `docs/quic-transport-design.md` §5.9 与 `third_party/quinn-proto/MIRAGE-PATCH.md`。

### 3.6 补丁后公网复测（2026-10-04 21:06–21:25，v0.15.1-4-ga7eb833，C1 → S1，丢包 5–20%）

QUIC 默认 8MB 窗口 + quinn-proto `MAX_CHUNKS` 补丁后，同时段交错（50MB；前 5 轮丢包 5–10%，后 3 轮 15–20%；Mbps）：

| 组合 | 前 5 轮 | 后 3 轮 | 服务端 CPU s/GB |
|---|---|---|---|
| **Mirage QUIC 定速 100** | **78 / 78 / 83 / 80 / 83** | **82 / 79 / 84** | **54–56** |
| sing-box hysteria2（100） | 67 / 76 / 78 / 77 / 76 | 78 / 76 / 78 | 66–79 |
| Mirage QUIC erasure | 68 / 64 / 64 / 61 / 65 | 67 / 79 / 79 | 57–70 |
| Mirage TCP + brutal 100 | 77 / 77 / 18 / 11 / 7 | — | 13–16 |

内存 RSS：Mirage 空闲 11MB、峰值 36MB（8MB 窗口）；sing-box 42MB → 63MB。客户端无连接错误日志。

对比补丁前同线路（§3.4）：定速 58–76 → **78–84**，erasure 31–63 → 61–79；hysteria2 本轮 67–78。**补丁后 Mirage QUIC 定速在公网上反超 hysteria2，服务端 CPU 少约 20%。**

### 结论

- **TCP 侧 Mirage 全面不输**：与同为伪装 TLS 的 anytls + REALITY 相比，回环吞吐约 2×、服务端 CPU 约 ½；与无伪装的 ss2022 相比吞吐持平或略高、服务端 CPU 持平、客户端 CPU 少约 25%。
- **brutal 路径 CPU 省约 55–65%**（sing-box 的 brutal 必须叠 h2mux）。
- **内存约为 sing-box 的 1/3–1/5**。
- **QUIC 侧**：原先落后 hysteria2（51 vs 81 Mbps）；定速模式后公网 58–76 vs 77–90（§3.4）；定位到 quinn 乱序段上限并打补丁、默认窗口改 8MB 后，实验环境中与 hysteria2 持平（§3.5），公网复测反超（定速 78–84 vs 67–78，服务端 CPU 少约 20%，§3.6）。

## 4. brutal 与系统默认 CC（BBR）

同一服务端、同时段交错测得的 Mbps（S1）：

| 场景 | 不开 brutal（BBR） | brutal 100 |
|---|---|---|
| 白天，丢包 ≈ 5% | 78 / 42 / 28 / 36 / 31 | 29 / 57 / 19 / 32 / 43 |
| 晚间，丢包 10–20% | 16 / 59 / 55 / 26 | 14 / 16 / 37 / 34 |
| 晚间，丢包 ≈ 5% | 22 / 33 / 27 | 41 / 42 / 42 |
| 晚间，C1 | 5 / 20 / 6 / 43 | 29 / 33 / 39 / 13 |
| 晚间，C2 | 20 / 17 / 13 / 12 | 25 / 22 / 19 / 22 |
| 白天，链路干净（另日） | — | 90–96（≈ 上限） |

- brutal 的主要收益是**稳定**：BBR 在丢包线路上 5–59 Mbps 大幅摆动，brutal 波动小得多；5 组对比中 brutal 3 组占优、1 组持平、1 组落后。
- brutal 速率是**硬上限**：链路干净且带宽富余时，BBR 可超过它。
- 速率**设高了会自伤**：此前（2026-09-07）同类跨境线路实测 rate=200 时重传 ≈ 30%，吞吐反不如 100；rate=50 则被限在 ≈ 48。

**取值建议**：`brutal_rate_mbps` 取客户端**实际能跑到的跨境带宽**（而非 VPS 端口速率），跨境丢包线路一般 50–150，不建议超过 200。`install.sh` 默认值据此由 50 调为 100。

## 5. 多版本对比（v0.5 → v0.15.2）：性能与抗审查是否随迭代提升（2026-10-04 / 05）

### 方法

- **版本**：v0.5.0-alpha.5 / v0.6.9 / v0.8.1 / v0.10.8 / v0.12.1 / v0.14.1 / v0.15.2（每个大版本一个代表），全部使用 GitHub release 的 musl 二进制（SHA256 校验通过），客户端与服务端同版本。
- **服务端**：S1、S2 上每个版本一个独立进程、独立端口（不开 brutal / brutal 100 各一个入站），不改动生产服务。服务端用一个 Python `AF_PACKET` 脚本记录所有新建连接（SYN），用来发现陌生 IP 的回连。
- **客户端**：**C2（国内直连，穿过 GFW）为主**，C1（经网关代理）作对照；每轮随机打乱「版本 × 服务器 × 模式」28 个组合的顺序，各做 TCP 连通、5 次经隧道 HTTPS（TLS-in-TLS）、10MB 下载。
- **抗审查静态测试**（C2 发起）：主动探测回应、原样重放、OpenGFW 内置分析器离线判定、ClientHello 与 ServerHello 特征。OpenGFW 判定使用 `analyzer/tcp/{fet,trojan}.go`（HyNetworks/OpenGFW）的 Python 移植，先用 sing-box Trojan 的真实流量验证：5 条连接 5 条命中。

### 5.1 直连穿 GFW 的长时间观测（C2，2026-10-05 00:05–01:13，约 1 小时）

| 服务端 | 各版本 HTTPS 成功率 | TCP 连通 | 下载中位（不开 brutal / brutal 100） |
|---|---|---|---|
| S1 | 全部 100%（每版本 120 次） | 168/168 | 13.7–18.9 / 14.2–17.2 Mbps |
| S2 | 98.3–100%（仅 v0.12.1 一次 TLS 错误；v0.14.1 一次 TLS 错误、一次超时） | 167/168 | 14.8–16.4 / 16.4–20.1 Mbps |

- 没有任何版本被封锁、限速或出现越来越差的趋势；吞吐被 C2 线路约 20 Mbps 的带宽封顶，各版本无差别。C1 对照组各版本也都在 76–113 Mbps（brutal 79–85），同样无差别。
- **未观察到 GFW 主动探测**：排除测试客户端的出口后，两台服务端只记录到 5 次陌生连接，来自 Censys（AS398324）与 Google Cloud 上的扫描器，且都打在编号最小的两个端口上，属于常规扫描。

### 5.3 抗审查静态测试（C2 → S1）

| 测试 | v0.5 … v0.14.1 | v0.15.2 |
|---|---|---|
| TLS 探测（证书 / 版本 / 套件 / ALPN） | 与真实伪装站一致 | 一致 |
| HTTPS 请求探测 | 与真站一致（301） | 一致 |
| 明文 HTTP 探测 | **0 字节，连接挂到 5s 超时**（真站回 14 字节后关闭）→ 可区分 | 14 字节后关闭，与真站一致 |
| 600 字节随机数据探测 | **0.2s 后 RST**（真站回 14 字节后关闭）→ 可区分 | 与真站一致 |
| ServerHello key_share 跨连接是否重复 | **重复：7 次握手仅 3–5 个不同值**（真实服务器每次都是新值）→ 被动可辨 | 7/7 全不同 |
| 原样重放（录下合法连接原样重发，看请求是否被再次执行） | 全部被拒 | 被拒 |
| OpenGFW fet / trojan | 0 命中（trojan 35 条可判定连接 0 中） | 0 命中 |
| ClientHello | 现代 Chrome 特征（GREASE / ECH / ALPS / X25519MLKEM768），JA3 每连接随机 | 同 |

### 结论

1. **v0.15 的安全修复最有价值，且为实测确认**：旧版本存在两处可被低成本利用的识别面——一次明文 HTTP 探测即可与真站区分，被动观察几次握手即可发现 key_share 重复；v0.15 修复了这两项（对应 2026-09-27 审计的两条 P1）。
2. **基础抗识别能力自 v0.5 起已具备**：TLS 外观与真站一致、能防原样重放、OpenGFW 内置分析器识别不了、ClientHello 为现代 Chrome 特征。所以 1 小时直连观测中所有版本都未被封锁或探测；旧版本的识别面需要有针对性的探测或被动规则才能利用，本次未触发不代表不存在。
3. **TCP 性能的迭代收益为零**（持平）；唯一显著的性能提升是 v0.15.2 的 QUIC 定速与 quinn 补丁。
4. **局限**：直连观测仅约 1 小时、单一时段（深夜）、单一客户端线路；v0.15 的会话新鲜性修复针对「替换随机数后重放」这类更隐蔽的攻击，原样重放测试覆盖不到。晚高峰的直连复测结果见 §5.4。
